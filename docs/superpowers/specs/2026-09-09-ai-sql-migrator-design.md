# SQLMigrator — AI-assisted migration script generator

**Date:** 2026-09-09
**Status:** Approved design, ready for implementation planning
**Scope:** Proof of concept

## 1. Purpose

Point the tool at two SQL Server databases. It reads both schemas, asks a language model
how the source maps onto the target — including transformation rules, not just one-to-one
column pairs — proves every proposed expression against the real database, shows you the
result for review and correction, and then generates a T-SQL migration script.

The tool never writes data to any database. Its output is a `.sql` file and the mapping
that produced it.

### In scope

- SQL Server on both ends
- Schema introspection of both databases
- AI-proposed table matching and column mapping, including transformation rules
- Machine validation of every proposed expression before a human ever sees it
- A review screen where proposals are corrected and accepted
- An approved mapping persisted as XML, from which the script is regenerated deterministically
- Generation of a reviewable T-SQL script

### Not in scope

Deliberate exclusions. Each has a known cost and none would require reworking this design.

| Excluded | Consequence |
|---|---|
| Executing the migration | The tool emits a script; a human runs it. Nothing is ever written to a database by the tool. |
| Joins across source tables | Each target table is filled from exactly one source table. |
| Row filters (`WHERE`) | Whole tables are copied, or not at all. |
| Aggregation / row reshaping | One source row produces one target row. No `GROUP BY`, no fan-out. |
| Key remapping / FK rewiring | Primary keys are preserved as-is. See §2.1. |
| Schema creation (`CREATE TABLE`) | The target schema must already exist. |
| Engines other than SQL Server | `Microsoft.Data.SqlClient` is used directly, with no provider abstraction. |
| Schemas above roughly 50 tables per side | Both schema summaries are sent in one prompt. See §2.4. |

## 2. Constraints and decisions

### 2.1 Primary keys are preserved, not reassigned

Migrated rows keep the primary key values they had in the source. The generated script
wraps each table in `SET IDENTITY_INSERT … ON/OFF` where the target has an identity
column among the mapped ones.

This keeps foreign keys valid for free: a child row's foreign key still points at the
same number it always did, so nothing needs rewriting. The price is that the target
tables must be empty when the script runs.

### 2.2 The model proposes; it never has the last word

The model produces structured JSON describing intent and a SQL expression. It does not
produce the migration script. The script is generated by deterministic code from an
approved mapping file, so it is reproducible, diffable, and identical on every run for a
given mapping.

Handing the model SQL *expressions* is a deliberate narrowing of the risk: an expression
is a fragment inside a `SELECT` list, and §5 proves each one compiles before it is
offered for review.

### 2.3 A browser cannot reach SQL Server, and must not hold an API key

Angular runs in a browser: it can neither open a socket to a database nor be trusted with
the NVIDIA key. The Angular application is a UI over a local backend that holds both
database connections and the key. "Angular app" here means *Angular UI plus a .NET
backend, served from localhost*.

### 2.4 Small schemas, single-prompt matching

Under roughly 50 tables per side, both schema summaries fit in one prompt, so the model
sees the whole picture when matching tables. This is what keeps the pipeline simple: no
chunking, no candidate shortlisting, no embedding index. Above that size the table-matching
pass would need deterministic shortlisting first; that is out of scope (§1).

### 2.5 Source and target may be on different instances

A T-SQL script can read the source directly only when both databases sit on the same
instance (three-part naming). Across instances it needs a linked server (four-part
naming). The generator therefore takes a configurable **source reference prefix**:
`[SourceDb]` for same-instance, `[SRCLINK].[SourceDb]` for cross-instance. One setting,
both cases covered.

### 2.6 Windows authentication to SQL Server

Both connections use `Integrated Security=true`. No database credential is typed, stored,
or transmitted, and none appears in generated output.

## 3. Architecture

```
D:\SQLMigrator
  src/
    SqlMigrator.Core/        schema reader, mapping model, expression validator, script generator
    SqlMigrator.Ai/          NIM client, prompts, structured-output contracts
    SqlMigrator.Api/         ASP.NET Core minimal API; serves the built Angular app
    SqlMigrator.Core.Tests/
    SqlMigrator.Ai.Tests/
  web/                       Angular 20 + Angular Material
  mappings/                  migration.xsd and saved mapping files
  fixtures/                  demo source and target databases
  docs/                      this document and its successors
```

**`Core` does not reference `Ai`.** The mapping model, expression validation and script
generation all operate on a mapping regardless of whether a model or a person produced
it. This makes the entire tool testable without an API key, and means the AI can fail, be
switched off, or be replaced without the tool becoming useless.

**`Ai` does not reference `Microsoft.Data.SqlClient`.** See §11 — this is the structural
guarantee that no data row can reach the model.

`Api` binds to localhost only, holds one analysis session in memory, and serves the
Angular bundle from `wwwroot`. It has no database of its own.

**Technology:** .NET 10 (SDK 10.0.301 present), `Microsoft.Data.SqlClient`, Angular 20
with Angular Material (Node 24.16 / npm 11.13 present).

### 3.1 Development loop

`ng serve` on port 4200 proxying `/api` to the API. For a packaged run, `ng build` outputs
into `src/SqlMigrator.Api/wwwroot` and `dotnet run` serves everything from one origin.

## 4. Pipeline

Seven steps, of which two involve the model.

1. **Read both schemas** — tables, columns (name, type, length, precision, nullability,
   identity), primary keys and foreign keys, from `sys.tables`, `sys.columns`,
   `sys.foreign_keys`, `sys.identity_columns`. No data is read.
2. **Match tables** *(model)* — one call carrying both schema summaries. Returns table
   pairs, each with a confidence and a one-line reason.
3. **Map columns and propose rules** *(model)* — one call per matched table pair. For each
   target column: a source expression, a rule kind, a confidence and a reason.
4. **Validate every expression** (§5) against the live source database.
5. **Review** (§8) — correct and accept.
6. **Save the approved mapping** as XML (§7).
7. **Generate the script** (§9) deterministically from that XML.

Steps 6 and 7 are pure functions of step 5's output. The script can be regenerated
forever without another AI pass, and a mapping the model got subtly wrong can be
hand-edited in the XML.

## 5. Expression validation

Every expression passes three gates, in order, before it appears on the review screen.
Failing any gate does not discard the row: it is shown flagged and unaccepted, with the
error, because the model's *intent* is frequently right when its SQL is not — and that is
precisely the row a human should fix.

1. **Textual screen.** Reject statement terminators, comment markers, and DDL/DML
   keywords (`INSERT`, `UPDATE`, `DELETE`, `DROP`, `EXEC`, `MERGE`, …). An expression must
   stay an expression.
2. **Compilation.** `SELECT TOP 0 <expression> FROM <source table>`. SQL Server itself
   confirms syntax, that every referenced column exists, and what type the expression
   yields. Reads no rows and costs effectively nothing.
3. **Type check.** The result type from gate 2 against the target column: incompatible
   categories block; a narrowing conversion (`nvarchar(200)` into `nvarchar(100)`,
   `decimal(18,4)` into `decimal(9,2)`) is a warning.

The same validation endpoint backs live re-validation when a human edits an expression in
the review grid, so a correction is confirmed as it is typed.

### 5.1 Mapping-level issues

Beyond individual expressions, the following are surfaced on the review screen:

| Severity | Condition |
|---|---|
| Blocking | A target column is `NOT NULL`, has no default, and nothing is mapped to it |
| Blocking | Two entries map to the same target column |
| Blocking | An expression failed any gate in §5 and has not been corrected |
| Blocking | A foreign-key cycle prevents a valid table order (§9) |
| Warning | Narrowing conversion |
| Warning | A source table matched to nothing |
| Warning | A proposal below the confidence threshold has not been reviewed |
| Informational | `IDENTITY_INSERT` will be used on this table |

## 6. AI integration

**Provider.** NVIDIA NIM over its OpenAI-compatible HTTP surface, base URL configurable
and defaulting to `https://integrate.api.nvidia.com/v1`. Because the surface is
OpenAI-compatible, switching to a self-hosted NIM container — or any other provider — is
a configuration change, not a code change.

**Credentials.** The key is read server-side from `NVIDIA_API_KEY` or from a gitignored
local settings file. It is never sent to the browser, never logged, and never returned by
any API endpoint.

**Model selection is configuration, not code.** The requirement is an instruct model with
reliable JSON-mode output. The exact identifier is chosen against the live NIM catalogue
during implementation rather than fixed here from memory, and the acceptance criterion is
concrete: the chosen model must pass the AI contract tests in §12 and produce parseable
structured output for the fixture schemas in §10 without retry.

**Structured output.** Every call requests JSON conforming to a declared schema. A
response that fails to parse is retried once and then reported as a failed table pair —
never guessed at, never partially applied.

**What the model receives:** table names, column names, data types, lengths, nullability,
and key information. **What it never receives:** a data row, a value, or a sample. See
§11.

**Confidence is a hint, not a verdict.** Proposals at or above the threshold arrive
pre-accepted in the review grid; anything below arrives unaccepted and requires an
explicit click. No mapping is ever applied because the model expressed certainty.

## 7. The mapping file

```xml
<migration name="Demo" generated="2026-09-09T11:14:00Z" model="…">
  <source database="SqlMigratorDemo_Source" reference="[SqlMigratorDemo_Source]" />
  <target database="SqlMigratorDemo_Target" />

  <table source="dbo.Customer" target="dbo.Client" confidence="0.96" origin="ai">
    <reason>Both hold one row per customer, with matching key and name columns.</reason>

    <column target="ClientId"    rule="copy"     expression="CustomerId" origin="ai" />
    <column target="FullName"    rule="concat"   expression="CONCAT(FirstName, ' ', LastName)" origin="ai" />
    <column target="ShortName"   rule="truncate" expression="LEFT(LastName, 20)" origin="human" />
    <column target="Active"      rule="case"     expression="CASE WHEN IsActive = 1 THEN 1 ELSE 0 END" origin="ai" />
    <column target="MigratedUtc" rule="constant" expression="SYSUTCDATETIME()" origin="human" />

    <unmapped target="Notes" reason="No corresponding source column; target column is nullable." />
  </table>
</migration>
```

An XSD at `mappings/migration.xsd` defines the grammar and is checked on load.

Three attributes earn their place. `rule` (`copy`, `truncate`, `concat`, `split`, `case`,
`constant`) records the model's stated intent, which makes the file readable and lets the
review grid group and explain itself — the generator uses only `expression`. `origin`
(`ai` or `human`) records who produced each line, making the file an audit trail of what
was actually approved. `<unmapped>` states explicitly that a target column receives
nothing, rather than leaving its absence ambiguous.

## 8. Review screen

Four steps: **Connections → Analyse → Review → Script**. Angular Material supplies the
stepper, grid, chips and progress indicators.

**Connections** — source and target panels (server, database, Windows auth), each with a
Test button returning the SQL Server version and table count.

**Analyse** — runs the pipeline steps 1 to 4 with progress, since the per-table-pair calls
take real time. Failures on individual pairs are reported without aborting the rest.

**Review** — split in two. Left: matched table pairs with confidence and reason, each
accept/reject. Right: the column grid for the selected pair — target column with type and
nullability, rule, expression (editable inline), confidence, validation status, and the
model's reasoning. Editing an expression re-validates it live against the source database.

Two further panels carry equal weight, because what the model *did not* map matters as
much as what it did: **unmatched source tables**, and **unmapped target columns**. A
`NOT NULL` target column with no default and nothing mapped to it appears here as a
blocker.

A verdict bar sits above everything — *"12 of 14 target tables mapped · 3 columns need
attention"*. Generate stays disabled while any blocking issue (§5.1) stands.

**Script** — the generated SQL with syntax highlighting, plus Download and Copy.

## 9. Script generation

Tables are emitted in a **topological sort of the foreign-key graph**. Unlike a
hand-authored mapping there is no document order to trust, so the generator derives one. A
foreign-key cycle among the mapped tables makes a valid order impossible, so it is a
blocking issue (§5.1) and no script is produced — rather than emitting something that
cannot run.

```sql
-- Generated 2026-09-09T11:14Z from mappings/demo.xml (sha256 3f9a…)
-- Source: SRV01\SQL2022 . SqlMigratorDemo_Source
-- Target: SRV01\SQL2022 . SqlMigratorDemo_Target
-- Review before running. This script inserts data.

SET XACT_ABORT ON;
BEGIN TRANSACTION;

IF EXISTS (SELECT 1 FROM [dbo].[Client])
    THROW 50001, 'Target table dbo.Client is not empty. Keys are preserved, so a rerun would collide.', 1;

SET IDENTITY_INSERT [dbo].[Client] ON;
INSERT INTO [dbo].[Client] ([ClientId], [FullName], [ShortName], [Active], [MigratedUtc])
SELECT [CustomerId], CONCAT([FirstName], ' ', [LastName]), LEFT([LastName], 20),
       CASE WHEN [IsActive] = 1 THEN 1 ELSE 0 END, SYSUTCDATETIME()
FROM [SqlMigratorDemo_Source].[dbo].[Customer];
SET IDENTITY_INSERT [dbo].[Client] OFF;
PRINT CONCAT('Client: ', @@ROWCOUNT, ' rows');

COMMIT;
```

- **One transaction for the whole migration.** A human runs this script; a half-migrated
  database is the worst available outcome.
- **An emptiness guard per target table.** §2.1 preserves primary keys, so running against
  a non-empty target is a guaranteed key collision partway through. The script refuses at
  the start instead, with a message that says why. This is the one place the generated
  script checks state rather than simply asserting it.
- **`IDENTITY_INSERT`** per table where the target has an identity column among the mapped
  ones, preserving keys per §2.1.
- **The source prefix** is the configurable value from §2.5.
- **The header** records source, target, timestamp, model, and the SHA-256 of the mapping
  file, so a script can always be traced back to the mapping that produced it.
- **No credentials appear in the output**, ever.

## 10. Demo fixtures

The tool never creates schema (§1); in production both databases exist. For the POC they
do not, so the repository carries scripts that build a pair. These are demo scaffolding,
explicitly outside the engine.

They are built to give the model real work rather than a trivial rename:

`fixtures/source.sql` → `SqlMigratorDemo_Source`

- `dbo.Customer` — `CustomerId int IDENTITY` PK, `FirstName nvarchar(100)`,
  `LastName nvarchar(100)`, `Email nvarchar(200) NULL`, `Description nvarchar(400) NULL`,
  `IsActive bit`, `CreatedUtc datetime2`
- `dbo.Order` — `OrderId int IDENTITY` PK, `CustomerId int` → Customer,
  `OrderDate datetime2`, `Total decimal(18,2)`
- `dbo.OrderLine` — `OrderLineId int IDENTITY` PK, `OrderId int` → Order,
  `Product nvarchar(100)`, `Qty int`, `UnitPrice decimal(18,2)`

`fixtures/target.sql` → `SqlMigratorDemo_Target`

- `dbo.Client` — `ClientId int IDENTITY` PK, `FullName nvarchar(200)` (needs a **concat**),
  `ShortName nvarchar(20)` (needs a **truncate**), `EmailAddress nvarchar(200) NULL`,
  `EmailDomain nvarchar(100) NULL` (needs a **split** — the part of `Email` after `@`),
  `Summary nvarchar(100) NULL` (**narrowing** from `Description`), `Active bit`
  (needs a **case** from `IsActive`), `CreatedUtc datetime2`,
  `MigratedUtc datetime2` (needs a **constant**),
  `Notes nvarchar(500) NULL` (**no source at all**)
- `dbo.Order` — as source but carrying `ClientId` rather than `CustomerId`
- `dbo.OrderLine` — renamed columns only

Between them these exercise every rule kind, the narrowing warning, and the unmapped-column
panel, so a demo has something real to show on each screen. Volumes are modest and all
data is synthetic.

## 11. Security

- **No data row can reach the model — structurally.** `SqlMigrator.Ai` has no reference to
  `Microsoft.Data.SqlClient`. It receives metadata objects and returns proposals; it cannot
  read a row even by mistake. This is a guarantee of the project graph, not of care.
- **Schema metadata does leave the machine** when the hosted NIM endpoint is used: table
  names, column names, types, keys. This is an accepted, knowing trade; a self-hosted NIM
  container removes it via configuration alone (§6).
- The NVIDIA key is server-side only, gitignored, never logged, never returned by an
  endpoint, never sent to the browser.
- Windows authentication to SQL Server; no database credential is stored or typed (§2.6).
- The API binds to localhost only.
- Generated scripts contain no credentials.
- The POC runs against the synthetic fixtures in §10, never a production instance.

## 12. Testing

- **Unit, no database, no API key** — XSD validation, mapping parsing, the textual
  expression screen, type compatibility, the topological sort, and golden-file tests over
  generated SQL. `Core` is fully testable in isolation because it does not depend on `Ai`.
- **Integration against LocalDB** — build the fixtures, then: the schema reader against a
  real database; the `SELECT TOP 0` validator against both valid and deliberately invalid
  expressions; and, most importantly, **execute the generated script** and assert row
  counts and per-column checksums. A generator whose output nobody ran is worth very
  little.
- **AI contract tests** — recorded responses, so CI needs no API key. Covers a well-formed
  response, a malformed one (must retry once then report), and a response naming a column
  that does not exist (must be caught by §5 and surfaced flagged).
- **API** — `WebApplicationFactory` over the endpoints.
- **UI** — component tests for the review grid and the issue panels. No end-to-end browser
  suite for a proof of concept.
